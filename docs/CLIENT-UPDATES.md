# Windows 客户端更新设计

## 目标

客户端更新必须满足以下条件：

- 用户只看到 `Pmman Network`，不需要手动下载 DLL、WireGuard 或 WebView2。
- 更新包由主控统一发布，客户端只通过主控 HTTPS 获取版本信息和安装包。
- 下载前验证版本签名，下载后验证文件大小、SHA-256 和签名；校验失败不得执行。
- 更新不破坏当前用户登录信息、P2P 开关、节点选择和本地诊断配置。
- 更新过程中不能留下旧的后台服务、WireGuard 隧道或半替换文件。
- 更新失败可以自动恢复上一版本；主控不可达时仍能继续使用当前版本。
- UI、后台服务、协议和安装包必须作为一个兼容版本发布，禁止只更新其中一个组件。

## 发布模型

主控新增客户端发布目录，例如：

```text
/opt/pmman-network-dev/client-releases/
├── stable/
│   ├── manifest.json                 # 当前最高版本指针
│   └── 0.2.0/
│       ├── manifest.json
│       └── Pmman-Network-0.2.0-x64-update.exe
└── beta/
    ├── manifest.json
    └── 0.3.0-beta.1/Pmman Network_0.3.0-beta.1_x64-setup.exe
```

每个渠道的根清单指向当前最高版本，旧版本清单和包保留在自己的版本目录中。
发布清单使用签名的 JSON；签名私钥不进入客户端源码、管理页面或日志：

```json
{
  "product": "pmman-network-client",
  "channel": "stable",
  "version": "0.0.1-alpha",
  "minSupportedVersion": "0.0.1-alpha",
  "mandatoryAfter": null,
  "installerFile": "0.0.1-alpha/Pmman-Network-0.0.1-alpha-x64-update.exe",
  "size": 123456789,
  "sha256": "...",
  "signature": "base64-ed25519-signature",
  "publishedAt": "2026-10-06T12:00:00Z",
  "releaseNotes": ["修复连接稳定性", "改进节点切换提示"]
}
```

生产发布使用独立的 Ed25519 发布私钥。签名内容是除 `signature` 外的规范化清单，客户端内置公钥；HTTPS 和 SHA-256 是传输/文件完整性校验，Ed25519 是发布者身份校验，三者缺一不可。

## 主控接口

客户端更新检查不依赖用户登录，避免用户因为 token 过期而无法获得安全修复。接口只返回公开的版本元数据：

```text
GET /v1/client/releases/{channel}/latest?platform=windows&arch=x64
```

响应为：

```json
{
  "available": true,
  "manifest": { "...": "..." },
  "download": "/v1/client/releases/stable/0.2.0/download"
}
```

下载安装包：

```text
GET /v1/client/releases/{channel}/{version}/download
```

要求：

- 只允许清单中登记的文件名，禁止路径穿越和任意文件下载。
- 响应带 `Content-Length`、`ETag`、`Cache-Control` 和版本头。
- 下载接口不接受或记录用户 bearer token。
- 返回的字节必须与清单大小和 SHA-256 一致。
- 节点资源接口和客户端资源接口分开，不能复用节点 token 权限。

管理端增加“客户端版本”页面，支持 stable/beta 版本列表、创建、编辑、删除，显示 SHA-256、发布时间、最小支持版本、强制更新时间和更新日志，并可上传轻量 `.exe` 更新包。主控使用部署时配置的签名私钥在线签名清单；私钥只保存为主控项目目录下的 0600 文件，不进入源码、管理页面、客户端或日志。生产环境应替换为 KMS/HSM 签名服务。

## 客户端运行流程

### 检查时机

客户端每次启动执行一次更新检查；设置页“关于”区域显示当前版本、最近一次状态同步时间和“检查更新”入口。发现版本后自动弹窗，用户可以稍后处理；主窗口的更新操作沿用同一 IPC 状态。

检查失败只记录“暂时无法检查更新”，不影响连接。使用指数退避，最长 30 分钟，避免主控故障时产生请求风暴。

### 下载和校验

下载在后台线程执行，保存到：

```text
%ProgramData%\PMMan\updates\<version>\ready.exe
```

流程如下：

1. 解析并比较 SemVer，禁止降级；当前版本小于 `min_supported_version` 时标记为强制更新。
2. 使用内置 Ed25519 公钥验证规范化清单签名。
3. 通过 HTTPS 流式下载；后台服务持续更新 IPC 状态中的真实百分比，UI 轮询并显示进度条。
4. 下载完成后重新计算文件大小和 SHA-256，并再次确认清单中的版本、平台和文件名。
5. 将下载文件原子移动为 `ready.exe`，写入仅供恢复使用的本地更新状态文件。

任何一步失败都删除未完成的临时文件，保留当前安装版本可用。

### 安装时机

普通更新采用“下载完成后提示，用户点击重启更新”。如果用户正在连接或有 P2P 会话，默认不强行中断：

- UI 显示“更新已准备，断开后安装”；
- 托盘菜单同样显示待更新状态；
- 用户明确点击“立即更新”时，先执行断开和 peer 清理，再退出并启动安装器；
- 关闭窗口只隐藏到托盘，不启动安装；选择“退出并更新”才执行。

强制更新仅用于安全或协议不兼容版本，`mandatory_after` 到期后才阻止新连接；已经建立的隧道不被后台强行拆除，用户断开或下次启动时完成更新。

## 原子替换与回滚

客户端安装目录保持由 NSIS per-machine 管理。更新器不是独立常驻程序，而是由当前客户端复制出的、一次性隐藏进程启动：

```text
Pmman Network
    -> 保存更新状态
    -> 断开隧道、停止后台 service
    -> 将当前 exe 复制到临时更新目录并启动独立更新器
    -> 更新器等待旧客户端退出
    -> 启动已校验的 NSIS 安装包（静默，仅必要时显示 UAC）
    -> 安装器替换 UI + service + 依赖
    -> 启动新客户端
    -> 新客户端报告启动成功
```

安装器使用 `/S` 静默升级参数，并把当前客户端可执行文件的父目录作为最后的 `/D=<install-dir>` 参数传给 NSIS；因此用户不会看到安装向导，也不会被要求重新选择目录。更新器不能直接从安装目录运行，否则 Windows 会锁住正在运行的 `pmman-client.exe` 并阻止 NSIS 覆盖它；现在更新器先复制到 `%TEMP%\Pmman Network\updater\<pid>`，替换完成后再启动安装目录中的新版本。per-machine 安装仍保留 Windows UAC；安装目录只允许安装器修改。更新日志写入 `%LOCALAPPDATA%\Pmman Network\update.log`，不记录用户密码、bearer token 或私钥。

新客户端启动后 60 秒内必须完成：

- WebView2 加载成功；
- 后台服务 IPC 可用；
- 版本与更新状态中的 `target_version` 一致。

若启动失败、IPC 不可用或版本不匹配，恢复流程由一次性恢复器执行：停止新进程，恢复上一安装目录/安装包，清除损坏的更新状态，再启动上一版本。更新器在安装器启动失败、超时或健康检查失败时也会自动重新启动旧客户端。恢复最多尝试一次，失败后保留诊断日志并不循环重装。

对于 `0.0.3-alpha` 及更早版本，轻量包的 NSIS hook 还包含兼容桥：识别旧版 `--apply-update` 父进程后交给 NSIS Restart Manager 释放旧主程序锁，并在安装完成后自动启动新客户端。之后版本使用临时目录中的独立更新器，不再需要该桥接路径。

当前本机已安装版本若低于 `0.0.3-alpha`，应发布包含兼容桥的更高版本；当前本地最新客户端为 `0.1.0-alpha`。不要继续复用此前已下载的旧版 `ready.exe`。`0.1.0-alpha` 包含用户自助修改密码入口、品牌和版本显示修复，并继续使用 Windows 原生进程句柄等待旧客户端、在更新器启动后立即终止旧 UI，修复 Tauri 优雅退出尚未完成导致的旧客户端锁文件竞态。

## 兼容性规则

- 客户端版本号、service 版本号、协议版本号和安装包版本号必须相同，构建脚本发布前检查四处版本一致。
- 主控 API 至少向后兼容两个客户端小版本；新增字段必须可选，不能破坏旧客户端解析。
- WireGuard 配置和地址租约格式变更必须先兼容旧客户端，再发布强制版本。
- P2P 协议变更沿用独立协议版本和 relay 回退；客户端更新失败时，旧客户端仍能走当前兼容的节点中转。
- 更新检查接口返回 `minSupportedVersion`，但主控不会把“有新版本”直接当作“撤销用户”。

## 发布流程

1. 在本地 Windows 构建 UI、service 和 Tauri 客户端，生成包含 WebView2、WireGuard runtime 的首次安装包，同时生成不重复携带这些依赖的轻量更新包。
2. 计算轻量包 SHA-256 和大小；管理后台创建/编辑版本时由主控使用受保护的发布私钥签名清单。
3. 先上传版本目录和版本清单，再通过原子 rename 切换渠道 `manifest.json`；不覆盖旧版本目录。
4. 使用测试渠道和专用账号验证安装、启动、IPC、真实 WireGuard 连接、断开和更新回滚。
5. stable 灰度发布，观察下载失败率、启动失败率、回滚次数和版本分布，再扩大范围。
6. 发布记录写入 `docs/PROGRESS.md`；签名私钥、token、账号密码和用户数据只存在忽略目录或发布机密钥库。

## 准出标准

- 新版本可以从主控获取清单，签名错误、SHA-256 错误和平台错误均被拒绝。
- 主控不可达时客户端可以正常启动和使用已有版本。
- 正在连接时不会被普通更新强制断开；手动确认后能完成断开、安装和重启。
- 更新后托盘、主窗口、后台 service、WebView2、WireGuard 隧道和 P2P 开关均正常。
- 模拟安装中断、文件锁、磁盘不足、UAC 取消和新版本启动失败，均能保留或恢复可用旧版本。
- 连续升级两个版本、跨重启升级和失败回滚至少各验证一轮。
